# Refactor ProjectDetailPage.tsx (componentes por tab + helpers, sin romper) — Plan de implementación

## Repository Research
`frontend/src/pages/ProjectDetailPage.tsx` actualmente tiene **5529 líneas** y contiene todo el flujo del proyecto en un solo archivo React FC:
- **7 tabs principales** (Documentos, Documento maestro, Reuniones, Temas, Aportes, Actividad, Equipo) con JSX inline dentro del mismo return.
- **Estado local denso**: ~70 useState (tabs, dialogs/modales, filtros, forms, context menus, resizer de árbol, states de reuniones expandidas, etc.) verificado por grep "const [.*] = useState" + queries/mutations (7 useQuery, 27 useMutation).
- **Acoplamiento tolerable**: El return renderiza cada tab con `{activeTab === 'X' && (...)}`; 4 tabs (docs/master/meetings/team) ya tienen implementación completa inline y 3 (topics/contributions/activity) caen en el fallback "Módulo en construcción" L3185-L3201.
- **Dependencias cross-tab existentes ya conocidas**:
  - `Documento maestro` llama `setActiveTab('docs')` y `setSelectedFolderId / setSelectedResource` (botón Abrir) → requiere callback prop.
  - El **header de proyecto** (L1575-L1762) usa `project / detail / canEdit / canManageMembers / canAdminMaster` y los setters de modal globales (`setShowNewFolder(false)`, `setShowFilePicker(true)`, open edit/delete meeting, favorito, editar proyecto).
  - El **árbol de carpetas** del tab Documentos (L1764-L1860) contiene FolderTreeItem + resizer (startResize/treeWidth), con dependencia de `selectedFolderId, folderTree, docMaestroCarpetaId, flatFolderById` y setters de context menus (`setFolderContextMenu` / `setFileContextMenu` / `setDocsAreaContextMenu`) y `setSelectedResource({type:file|folder, id, projectId})`.
  - **Modales globales**: están fuera de los tabs al final del return (L3203+); muestran diálogos `NewFolder / MasterSelector / InviteMember / FilePicker / DeleteFile / MoveFile / Rename / ConfirmClearMaster / edit&delete meeting etc`. **NO se tocan** en este refactor (responsabilidad del ProjectDetailPage padre); solo se delegan a props callbacks.
  - **Reutilización helpers locales**: `initials / iconForKind / colorForKind / fileKind / formatBytes / formatRelativeTime / meetingStatusLabel / meetingStatusBadgeClass`. `FolderTreeItem / MasterFolderTreeItem` ya existen como pequeños componentes locales en la parte superior del archivo.
- **Convención de nomenclatura**: `frontend/src/components/layout/*` + `pages/*.tsx`. No hay carpeta `components/project` aún. Se seguirá el estilo PascalCase sin sufijo `index.ts` simple por componente (igual que `AppLayout.tsx`, `Topbar.tsx`).
- **Verificación pre-refactor (baseline conservada)**:
  - `cd frontend ; npm run typecheck` → 0 errores (verificado último commit `2009671`).
  - Runtime smoke manual posterior: login Carlos / expandir reunión / subir acta / vincular / desvincular.

## Dependencies and Considerations
- **React 18 / @tanstack/react-query / Vite / clsx + lucide-react / tailwind + utilities `btn-* input-base card`** se conservan igual. Todos los componentes nuevos son .tsx FC.
- **No mover ningún useQuery/useMutation "hacia abajo"** a menos que sea estrictamente necesario. Mejor orquestar todo en el padre y pasar props por valor o callbacks; esto evita romper `invalidateQueries` y `setPageToast` que están ligados al ProjectDetailPage.
- **`queryClient` y `setPageToast`**: se siguen consumiendo del padre; los subcomponentes no importan `useQueryClient` directamente a menos que sea para invalidate focalizado (no recomendado para este refactor inicial – pasar mutaciones vía callbacks `onSubmit` que el padre llama con `.mutate(...)`).
- **Tipos compartidos** (`ApiMeeting`, `ProjectMember`, `FolderTreeNode`, `ApiMeetingStatus`, `MasterDocInfo`, `ApiFile`, `useQuery` data shapes) ya existen en `../services/*` y se re-importan en subcomponentes. Si aparece un tipo `inferred` grande, usar los tipos `ReturnType<typeof XQuery>` o bien declarar tipos en el padre y exportarlos via types inline; **no se crea barrel `index.ts`** para evitar ciclos.
- **No se cambia el orden de los elementos HTML del padre** fuera de los bloques `{activeTab === X && ...}`. Esto minimiza el riesgo de ruptura visual o de estilos (`flex-1`, `overflow-y-auto scrollbar-thin`, `p-4 md:p-6`, `max-w-3xl mx-auto space-y-4`).
- **Riesgo scope creep**: El usuario preguntó por las 7 tabs marcadas – por tanto **NO se refactorizan modales** (NewFolder/FilePicker/EditProject). Si luego desean refactorizar modales, otro scope.

## Risks
- **Props drilling excesivo** en `ProjectMeetingsTab` y `ProjectDocsTab` (~40-50 props cada uno por state + setter + mutation data/pending). Mitigación: agrupar en objetos tipo `DocsTabProps` / `MeetingsTabProps` interface grande (no usamos `Context` para mantener responsabilidades claras y no cambiar patterns del repo).
- **Referencias a variables no-exportadas** de clausura (ej: `detail?.documentoMaestro`). Mitigación: tipar explícitamente las props con los tipos existentes y pasar valores ya resueltos (ej: `documentoMaestro={detail?.documentoMaestro ?? null}`).
- **Cambios de re-render**: al separar componentes, algunos renders pasaban por re-render del padre completo; ahora se restringen al subcomponente. Esto en general es bueno, pero puede revelar bugs de staleness en props – se cubre con el smoke manual.
- **Regresión modales**: Como no movemos modales, el riesgo es bajo. Solo se valida que al hacer click en "Agregar miembro" en `ProjectTeamTab` se dispare `onInviteMemberClicked={ () => setShowInviteMember(true); ... }` (callbacks del padre).
- **Cíclicos imports**: ProjectDetailPage -> components/project/* y ninguno importa ProjectDetailPage. El archivo `fileHelpers.ts` y `FolderTreeItem.tsx` no importan desde page.
